# Internal architecture

- `main.py` opens a startup/repair window before loading the optional GUI. Frozen builds verify and repair their bundled runtime offline. `--version`, `--health-check`, and `--ui-import-check` are non-interactive checks. The import check does not create a window and is not a visual GUI smoke test.
- The desktop UI is a frameless, pixel-styled window: bitmap-font chrome drawn on canvases, a compact source field (paste, URL, drag-and-drop, Browse fallback), an option row with the executor profile, the remote-payload switch and `script_key`, a segmented progress meter and a colour-coded activity log. Finished runs open automatically in the built-in viewer, which shows the recovered source with line numbers, Lua highlighting, search, copy, save-as and open-in-editor. Only `destroyed_N.lua` is written to `output/`; reports and any raw intermediates live under `logs/`. The main application runs as the current user; the separate setup program requests Administrator access to install files.
- `core.source_input` accepts direct HTTP(S) code links, common GitHub blob/Pastebin pages, and simple `loadstring`/`HttpGet` wrappers. It fetches text only, follows at most four linked layers, caps downloads at 16 MiB with request timeouts, validates redirects, and blocks local/private network targets. It never evaluates fetched source.
- `core.deobfuscator` is a bounded static Luau tokenizer and constant-expression evaluator. It folds supported literal/string, arithmetic, bit32, table-concat, and Base64 forms; unknown/dynamic expressions are retained. It is not a general Luau decompiler.
- `core.formatter` applies whitespace-only formatting while preserving the token stream and the author's line breaks between statements (newlines are trivia in Lua, so keeping them cannot change behaviour); continuation lines are joined and block bodies re-indented. It conservatively leaves interpolation strings, Luau `if` expressions, typed function return annotations, and inputs over its size limit unchanged. Static decoding is likewise only applied when it removes a real layer — escapes, hex, base64 or a minified one-liner — so an already-readable script is not rewritten. The pipeline writes a formatted candidate only if a local Luau compiler accepts it in compile-only mode; otherwise it keeps the already-validated candidate.
- `core.pipeline` orchestrates the routes: `core.engine` (layered recovery) for ordinary text, the vendored MoonSec V3 helper and the Luraph v15 lifter for recognized containers, and the `luau-decompiler` CLI for Luau bytecode. For Luraph v15 it routes supported structures to the vendored MIT lifter, which captures VM prototypes/opcodes and lifts their control flow into a readable Luau candidate. Reports include the lifter's function/block/jump counts, unresolved lazy constants, missing-value markers, and runtime functions the backend cannot reconstruct. Unused generated runtime error stubs are removed; any used unresolved runtime helper or unlifted VM block makes the result partial and moves it to a `.candidate.luau` artifact. Large `loadstring` bodies captured by the isolated Luraph harness are saved beside the report. Protez can use a captured body as source only when it is substantial, passes Luau compilation, has no supported-family signature, and does not fetch another remote Lua payload. A loader that calls `HttpGet` without embedding the response remains partial; its nested VM captures stay available as separate artifacts. Compile-only validation does not prove semantic equivalence. A pinned Luraph sample with a published original source is also executed side by side in Windows AppContainer smoke checks; that validates only the fixture's behavior. Other Luraph versions retain bounded static container extraction and an isolated wrapper attempt; those results are partial. One public Luraph v14.7 fixture was previously used to validate container extraction (`terrorlua/obfuscator-samples`, commit `a6ecd0ea7112c6a65d4b7acba40acc9e280301e3`, file `Luraph/v14.7/001163f72ed972da.lua`, input SHA-256 `9fe7a64c1cf1605002844ca0135fb8daf07ccc192f4bb4e52a405116440718f7`); the unpacker produced a 94,025-byte interpreter stream and a 2,224,577-byte custom-bytecode stream. A single supported fixture is not evidence of broad version/variant coverage.
- MoonSec V3 signatures route to a separate GPL-3.0 helper. It parses recognized wrappers statically, maps supported handlers to standard Lua 5.1 bytecode, then invokes pinned MIT `unluac-rs` in strict generation mode for readable source recovery. Key expressions use a restricted AST evaluator; wrapper code is never executed on this route. Luau syntax validity alone does not mark the result complete: generated unluac error comments, lifter errors, or nested `loadstring(HttpGet(...))` calls produce a `.candidate.lua`, a static preview, and explicit partial reasons. Recovered bytecode and disassembly remain available. Coverage is limited to the helper's known serializer and opcode patterns.
- Other text inputs go through `core.engine`, a layered recovery engine: bounded static decoding, remote payload resolution for thin loaders and private libraries, embedded-bytecode lifting, the portable backend, then the bounded native Luau worker. Each layer records its own hash and the report lists them; a layer is only accepted when it is a real improvement over the previous text.
- `core.vm_dump` installs a second step callback in the portable backend (chained with the instruction budget, so it cannot be cleared by a script) and snapshots the large array-like tables an obfuscator builds for its own VM: the call stack is walked from inside the hook, locals and upvalues are read with `debug.getlocal`/`debug.getupvalue` (a chunk's `what` is `main`, not `Lua`), each scan is bounded (512 scans, 160 reports, 96 table references) and guarded by `pcall`, and a table that was sampled while still being filled is re-read once it grows. Protez's own prelude tables are skipped. `core.vm_recover` turns the snapshots into the instruction stream (stride detection by opcode/operand column variance), an opcode histogram, a confidence value and a bounded disassembly listing; the report carries it under `vm`, and a partial result says so instead of pretending to have lifted the VM. `docs/FAMILIES.md` maps every supported family to its detection evidence and recovery path.
- `core.families.scan_embedded_source` recovers Lua **source** (not only bytecode) from numeric arrays, `string.char(...)` calls, Lua escape runs, hex and base64 blobs, which is how PSU, Nexus, WeAreDevs-style and home-made packers store their payload.
- `core.remote_payloads` resolves loaders whose payload lives behind an HTTP call (including Luarmor `api.luarmor.net` loaders): URLs are extracted or discovered at runtime by the fetch bridge and the `request` bridge (whose `{StatusCode, StatusMessage, Headers, Body, Success}` answers a loader can POST a `script_key` to), downloads are cached per run under `logs/remote_cache`, and the second native pass receives the captured bodies as `__protez_http_bridge` responses. `luarmor_signature()` describes a Luarmor loader without executing anything. This is the "API защита" case: the script body is never available as a raw link, so the only way to reach it is to run the loader with a working executor, and whatever it downloads, decodes or writes is captured as a recovery candidate.
- `core.families` classifies the input (Luraph v14/v15, MoonSec V2/V3, WeAreDevs v2.4, Wynfuscate v5, IronBrew 2/3, Prometheus, Nexus v2.0, PSU v1.0, AztupBrew, Xen, Synapse-protected payloads, generic custom VM) and finds Lua 5.1 chunks inside raw text, escapes, hex/base64 layers and decimal/hex byte arrays. `core.lua51` reads, disassembles and lifts those chunks into one-statement-per-line Luau; register names are synthetic and the result is labelled partial.
- Legacy route text inputs are still statically cleaned and compile-checked, then run in the bounded native Luau worker. The pipeline captures strings passed to real `loadstring`/`load`, compiles them with Luau, and returns executable functions so wrapper code can call them. It explores at most six payload layers and 20 candidates within 90 seconds. A valid source fallback is retained. Each worker run also writes a structured JSONL trace; reports list trace files, event counts, captured chunks, execution outcome, and isolation backend.
- `core.sandbox` requires `protez-native-host` and fails closed instead of invoking a normal Luau CLI. `io`, `os`, `package`, `dofile`, `loadfile`, and `require` are removed from the Luau worker. Scripts that depend on Roblox Engine services are served by `core.injector_env`, which injects an inert Roblox/executor prelude (proxy services, `game:HttpGet` routed to the bounded fetch bridge, `Instance.new`, scheduler shims, `bit32`/`utf8`/Luau library gaps) before the payload runs; the host itself still provides no Roblox globals.
- `core.emulator` is the portable backend for machines where the native worker or its isolation tools cannot start: a capability-stripped in-process Lua 5.1 interpreter with instruction and time budgets, no host filesystem/process access, fetch and `request` bridges, a recorded input surface, and capture of everything passed to `loadstring`/`load`/`string.dump`, downloaded bodies and files written through the executor API. Binary captures are transferred as hex and lifted by `core.lua51`. Its `workspace_dir` mirrors the virtual executor filesystem into `logs/executor-workspace/`, so a payload a loader only ever wrote to disk can still be recovered and inspected after the run. The reported emulator run is the richest one (the loader, not the tiny deobfuscated layer that follows it).
- `core.executor_api` is the executor command surface injected **after** `core.injector_env`'s Roblox/executor prelude and overriding its stubs: the default profile is **Real** (fictional, 144 features), with the file API, `request`/`HttpGet` tables, pure-Lua `crypt` (base64/hex/HMAC/SHA-256), identity/HWID/time functions, `hookfunction`/`hookmetamethod`/`newcclosure`/`getrawmetatable`/`setreadonly`, `debug` helpers and input recording. `hookmetamethod(game, "__namecall", hook)` and the classic `getrawmetatable(game).__namecall = hook` / `__index` swap both observe `game:HttpGet(...)` with the real arguments and a `getnamecallmethod()` that is set during the hook; a hook that throws falls back to the emulated call, so one broken dumper hook cannot end the run. `static_call`/`build_static_environment` fold the same names in the static evaluator so obfuscator probes see one consistent executor.
- Windows dynamic runs use a no-capability AppContainer, a Job Object with a 768 MiB process/job memory bound and one-process limit, redirected standard streams, and a parent-enforced timeout. Linux runs require `bubblewrap` and `prlimit`; they unshare network and other namespaces, expose the native host and input read-only, bind system runtime libraries read-only, and apply address-space, CPU, file-size, descriptor, and core-dump limits. Dynamic execution is unavailable when these isolation tools cannot start; there is no unsandboxed fallback.
- `native/host.cpp` builds the pinned Luau 0.740 compiler/VM with optimization level 0 and debug level 2. It caps VM allocator use at 256 MiB, dynamic chunks at 16 MiB, and trace events at 25,000 per run by default. Native traces record Luau VM PCs/opcodes, line and frame information, and sampled local values; they do not capture the full register file. `core.tracer` streams the records to rotating JSONL files.
- Protez has family-specific VM lifting for supported Luraph v15 and MoonSec V3 patterns. It does not provide a universal custom-VM lifter. Luau instruction tracing is supplemental behavior evidence and does not itself recover an obfuscator's custom opcodes. Source output is an approximation: names/comments and semantic equivalence are not guaranteed.
- Bytecode inputs (`.luac`, `.lbc`, `.bin`) are read by the built-in Lua 5.1 reader and lifted by `core.lua51` first; Luau bytecode containers stay on the local `luau-decompiler` CLI path in a temporary workspace. Bytecode and recovered source are not executed. The output is syntax-checked and formatting is only applied when the lifted listing is already valid Luau. Frozen Windows builds bundle the CLI from `PumbaaDev/luau-decompiler` commit `ee07098c31e11601a9ca434bc12932a4ded65f7b` and its MIT license notice; reports claim that provenance only when the active binary's SHA-256 matches the packaged copy. Decompilation and lifting are lossy: comments and local names are unavailable without debug metadata, and unsupported or shuffled bytecode yields partial code.
- `core.output` owns the artifact contract: exactly one `destroyed_N.lua` per run (index = highest existing + 1), a readable header banner describing family, method, injector profile, layers and notes, and an atomic write. Reports are written under `logs/`; legacy `deobfuscated_*`, `analysis_*.report.json`, `*.candidate.luau` and `captured_payload_*` artifacts are pruned or parked there.
- `installer.py` repairs source-checkout dependencies, Luau tools, and optional family-lifting tools with timestamped logs, subprocess timeouts, and a retry path. Frozen Windows builds bundle the Python/Tk runtime, native host, Luraph/MoonSec backends, both bytecode decompilers, third-party notices, and the GPL helper's corresponding source. The user does not need to install Python, pip, CMake, Rust, or .NET to use the frozen build. The optional `lupa` runtime that powers `core.emulator` comes from `requirements-portable.txt` and is installed best-effort; its absence only disables the portable backend.
- `.github/workflows/windows-installer.yml` builds the native, Rust, and MoonSec support tools in parallel, then packages x64 `Protez.exe`. The workflow attaches only `Protez.exe` to GitHub Releases.
