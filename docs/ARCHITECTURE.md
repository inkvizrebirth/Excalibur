# Internal architecture

- `main.py` opens a small startup/repair window before loading the optional GUI. Source checkouts can install Python dependencies and Luau tools; frozen builds verify and repair their bundled runtime offline. `--version`, `--health-check`, and `--ui-import-check` are non-interactive checks. The import check does not create a window and is not a visual GUI smoke test.
- The desktop UI is compact and square-cornered, with readable system/UI and monospace fonts, the sword application icon, and a simple animated rectangular outline. Paste, file, Browse fallback, optional `tkinterdnd2` drag-and-drop, queued logging, background processing, and the UAC Administrator manifest remain. Results open in the system text editor with an in-app fallback.
- `core.source_input` accepts direct HTTP(S) code links, common GitHub blob/Pastebin pages, and simple `loadstring`/`HttpGet` wrappers. It fetches text only, follows at most four linked layers, caps downloads at 16 MiB with request timeouts, validates redirects, and blocks local/private network targets. It never evaluates fetched source.
- `core.deobfuscator` is a bounded static Luau tokenizer and constant-expression evaluator. It folds supported literal/string, arithmetic, bit32, table-concat, and Base64 forms; unknown/dynamic expressions are retained. It is not a general Luau decompiler.
- `core.formatter` applies whitespace-only formatting while preserving the token stream. It conservatively leaves interpolation strings, Luau `if` expressions, typed function return annotations, and inputs over its size limit unchanged. The pipeline writes a formatted candidate only if a local Luau compiler accepts it in compile-only mode; otherwise it keeps the already-validated original candidate.
- For text input, `core.pipeline` checks for Luraph before compilation or sandbox inspection. `core.luraph_static` can statically unpack recognized LPH Ascii85 container layouts (single/two-stream Zstandard and legacy two-stream raw LZMA1/range data), with a 64 MiB per-stream output cap and a 12-second decompression budget. It writes intermediate VM-interpreter/custom-bytecode artifacts and an explicit partial report; it never runs the wrapper, interpreter, or payload. The extracted Luraph bytecode is not standard Luau bytecode and is not sent to the ordinary bytecode decompiler. Validation was performed statically on one public Luraph v14.7 fixture, `terrorlua/obfuscator-samples` commit `a6ecd0ea7112c6a65d4b7acba40acc9e280301e3`, file `Luraph/v14.7/001163f72ed972da.lua` (input SHA-256 `9fe7a64c1cf1605002844ca0135fb8daf07ccc192f4bb4e52a405116440718f7`): the unpacker produced a 94,025-byte VM-interpreter stream and 2,224,577-byte custom bytecode stream. The sample is not redistributed, and this single fixture is not evidence of broad version coverage. This is container extraction only—not VM lifting, source reconstruction, or a promise to support every Luraph build/version. Other text inputs are statically cleaned and compile-checked; bounded sandbox inspection can capture local loader payloads, with caps of six layers, 20 candidates, and 90 seconds. A valid source fallback is retained. In Administrator mode, sandbox execution and tracing are skipped. Syntax validity is not proof of complete deobfuscation.
- Bytecode inputs (`.luac`, `.lbc`, `.bin`) go through the local `luau-decompiler` CLI in a temporary workspace. The executable receives bytecode as data; Protez does not run the bytecode or recovered source. The CLI output is syntax-checked and any whitespace-formatted candidate is separately checked in compile-only mode. Input and output are limited to 64 MiB and the CLI has a 30-second default timeout. Frozen Windows builds bundle the CLI from `PumbaaDev/luau-decompiler` commit `ee07098c31e11601a9ca434bc12932a4ded65f7b` and its MIT license notice. Reports claim that provenance only when the active binary's SHA-256 matches the packaged copy; locally discovered binaries are marked unverified. The pinned upstream README documents bytecode versions 3–9; other versions and custom opcode schemes are not promised. Decompilation is lossy: comments and some names are unavailable without debug metadata, and unsupported or shuffled bytecode can yield partial or inaccurate code.
- `core.sandbox` runs the mock-runtime harness in a separate, time/output-limited process for eligible text-source inspection, captures locally produced `loadstring`/`load` payloads, and disables remote HTTP and module access. The Roblox-shaped API is a mock, not an OS security boundary; do not treat it as a safe general-purpose execution sandbox.
- When present, `tools/protez-native-host` (or `.exe`) runs the pinned Luau 0.740 compiler and VM. Compile-only checks load bytecode without executing a candidate. The host is built from `native/host.cpp` and compiled with optimization level 0 / debug level 2 for instruction tracing and local/upvalue names. Full register recovery, CFG lifting, VM-handler recovery, and source reconstruction are not implemented in Protez's native host.
- `core.tracer` streams validated hook/API and optional native VM events into rotating JSONL files. Stock Luau fallback traces do not include instruction stepping.
- `installer.py` repairs source-checkout dependencies and available Luau tools with timestamped logs, subprocess timeouts, and a retry path. Frozen builds bundle the Python/Tk runtime, mock runtime, native host, bytecode decompiler, and license notice; the user does not need to install Python, pip, CMake, or Rust.
- `.github/workflows/windows-installer.yml` builds x64 `Protez.exe` with the sword icon and `requireAdministrator` manifest, plus the separate setup executable. The setup executable remains a CI artifact; the workflow attaches only `Protez.exe` to GitHub Releases.
